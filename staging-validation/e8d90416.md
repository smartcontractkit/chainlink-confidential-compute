# Staging validation: bump-chainlink-a536af9

## Change

Bumps chainlink-common from `daa34bb8` to `f9f63cb6` in the confidential-workflows enclave app, nitro host, config-tracker, and enclave-client. The common range includes wasmtime v50 (#2497), a per-workflow wasm table-element limit (#2466), and wasmtime host instrumentation (#2474). Also bumps the chainlink core pin for E2E tests to `a536af9`; that part is test-only.

## Validation steps

- Deploy the new confidential-workflows and confidential-http enclaves to staging and confirm all enclaves come up and reach quorum.
- Watch the existing confidential-workflows and confidential-http canaries for at least a day.
- On the enclave dashboards, compare execution success rate, `/execute` p99 latency, and enclave memory against the previous release.
- In Loki, search confidential-workflows enclave logs for wasm/wasmtime errors, especially table-limit or instantiation failures.

## Success criteria

- Canaries stay green, with no new execution failures.
- Execution success rate and p99 latency stay within the previous release's range.
- Enclave memory stays in line with the current baseline, with no new growth over pod lifetime.
- No wasm table-limit or wasmtime instantiation errors in enclave logs.

## Edge cases and risks

- wasmtime v50 changes the native engine running workflow binaries inside the enclave; watch for compile/instantiate regressions or memory growth.
- The new table-element limit could reject large workflow binaries that ran before. Roll back if real workflows start failing with limit errors.
- Rollback: redeploy the previous enclave release.
