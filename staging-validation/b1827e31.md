# Staging Validation: CW Execution Limits

## Change

PRIV-716 / PRIV-683: two independent default-off booleans. DON `PerWorkflow.ConfidentialWorkflows.IncludeExecutionLimits` controls whether scoped HTTP/WASM values are included before signing. Gate and limits come from one ready source. Off removes caller-supplied limits and preserves legacy bytes/hash; on overwrites caller input with trusted values. Unready settings or an invalid gate fail system Unavailable before dispatch/signing; a loaded source without scoped opt-in is off. No core patch or timestamp prerequisite.

The host forwards signed requests unchanged after quorum. Enclave operator setting `enforceCRELimits` independently controls application of supplied values, default off. Off preserves legacy behavior; on applies supplied values including explicit zero/false, within safety ceilings. One snapshot per execution; changing this switch does not change signed bytes.

Ceilings: 128,000,000 bytes guest memory, injected execution timeout, 5 MiB response buffer and 1000 KiB HTTP response. Final-result rejection follows the supplied response-enforcement flag. User-metric enablement remains deferred pending bounded forwarding.

## Validation steps

- Deploy matching host/enclave, common and capability versions with both gates off. Verify every signer has new code and ready settings; off-state bytes/hash must match legacy throughout the rolling code upgrade.
- For any DON inclusion change in either direction: pause admission, drain executions including retries, change and verify settings/readiness across all signers, then resume. First enable inclusion while enclave enforcement stays off. Exercise both inclusion transitions in staging and verify off restores legacy bytes.
- Verify the complete authoritative settings on every signer. Env seeds the source; the first valid JD snapshot replaces it, not merges. If JD is authoritative, do not seed placeholder/incomplete env settings.
- Restart a JD-only plugin before delivering its first snapshot: execution must fail system Unavailable without dispatch. Deliver valid opt-in and overrides and retry a new execution; verify they are signed. A loaded empty source must omit limits. Explicit opt-in with no numeric overrides must send CRE defaults. A malformed gate must fail without dispatch; a schema-default-only opt-in must not enable inclusion. Failed snapshot updates retain the last good source.
- Confirm `cre_limits_policy{limits_present=true,enforced=false}` and successful executions exceeding CRE defaults.
- POST the complete enclave settings payload with `enforceCRELimits=true` to each canary host's loopback config-port `/settings`. Verify GET reports true. A flag-only payload is invalid. Use controlled canary routing; this flag affects every workflow on that enclave.
- With inclusion and enforcement on but no numeric overrides, run six HTTP calls and a 100 KB request: call 6 must fail at five calls; the request must fail at 10 KB. Confirm `cre_limit_exceeded` identifies the setting.
- With owner overrides of 20 calls / 200 KB, both must succeed. For the request-size check use an endpoint returning a small response, so HTTP response and guest-buffer limits do not mask the request override. An echo test needs matching response overrides, such as the fixture's ResponseSizeLimit=300kb and ExecutionResponseLimit=1mb. Exercise response size, timeout and explicit-zero limits separately. The checked-in e2e fixture instead uses a two-call override; its third call must fail.
- Exercise WASM memory, runtime, logs, concurrency and response-size boundaries. Compare response-enforcement true/false; oversized overrides cannot raise safety ceilings. Legacy requests with missing values remain compatible even with enforcement on.
- Keep signed values unchanged. Confirm each current host process logged `injected storage credentials into enclave` (or had no startup injector), then POST a complete settings payload with false. Verify every GET immediately and at least 30s later, and run new executions. An outstanding startup retry can otherwise restore the old flag. Remove/restart unresolved hosts with the desired complete settings before returning them to traffic. New snapshots use disabled-policy behavior without a request-hash change; in-flight work retains its snapshot.
- Persist false in the complete startup `ENCLAVE_SETTINGS` and restart the staging host process, not only the enclave. Require that new process's injection-success log, GET false, and a successful new execution before accepting persistence. An enclave-only restart does not rerun the host injector; its default false is not proof that settings were applied. Changing the environment alone does not update a running enclave.
- Verify PRIV-758 delivery for workflow-error ratios above baseline and HTTP violations. Watch node-side readiness/system errors, subscription failures, capacity and quorum failures; some WASM errors also use the system-error path.

## Success criteria

- Inclusion off produces legacy bytes/hash; on includes trusted scoped values. Unready settings or an invalid gate never dispatch or sign a request.
- All signers agree on request hashes after each coordinated inclusion change, including retries.
- Enforcement off ignores supplied values without bypassing safety ceilings; enforcement on applies them, including explicit zero/false.
- Customer overrides cannot raise the fixed memory, response-buffer or HTTP-response ceilings; runtime remains bounded by the injected timeout.
- Enforcement-only rollback changes no signed bytes or hashes. New executions recover; in-flight executions retain their policy snapshot.
- Monitoring distinguishes workflow errors, system errors and limit violations, and required staging alerts reach their receiver.

## Edge cases and risks

- Readiness distinguishes no source from loaded-empty, not stale from fresh or inter-node version agreement. A Store during resolution must not mix the gate or limit fields from two snapshots.
- Restarted signers must use JD-only startup or boot settings aligned with JD for the gate and all inherited limits in opted-in scopes. Under F+1, restart one signer at a time and verify its fresh snapshot and matching request hash before proceeding.
- The switch/readback are operator controls, not attested policy. Mixed host states can yield different outcomes for identical signed inputs. Track every serving host and failed acknowledgements before declaring rollback complete.
- The switch does not cancel in-flight work, invalidate replay caches or promise retries re-execute. Verify recovery on new executions.
- Malformed/failed settings updates preserve the previous flag. A successful complete payload omitting it disables enforcement.
- Inclusion flips in either direction, and limit overrides while inclusion is on, change hashes during DON propagation. Disable only enclave enforcement first for incident recovery, then coordinate updated values and validate before re-enabling. F+1 deployments can execute two hash groups; verify live quorum.
- Once inclusion is on, binary/common upgrades, compiled/environment defaults, resolver/clamping changes and new serialized fields can also change signed output. Use the same pause/drain including retries/update-all-signers/verify/resume protocol for any such change. Compare all 15 resolved fields across signers before activation, not just the explicit overrides.
- CRE-settings jobs and environment-default changes touching these shared keys need CW-owner approval for affected opted-in workflows, including changes requested for regular CRE. After resuming, verify the first canary has matching request hashes across signers and no quorum-timeout batch.
- Keep settings on the separate loopback config port, not a public shared-port/dev listener.
- Policy/violation events are not full usage telemetry. Define observation periods, numerical stop thresholds, rollout ownership and routing before production.
- Future trust-exception retirement requires a new accepted enclave image that always enforces signed values, mandatory-field validation if required, and removal of older flag-capable measurements. Not part of this rollout.
