# Staging validation: memory-budget-update

## Change

The confidential-workflows enclave derives execution and compilation capacities
from a shared static memory budget. Settings are capped to that budget, and
reinjection reuses the compilation semaphore instead of multiplying permits.

## Validation steps

### Automated admission proof

Follow the [capacity runbook](../tests/e2e/RUNBOOK.md#real-enclave-workflow-capacity-test)
for `make e2e-local-workflow-capacity` on a dedicated x86_64 Nitro test host or
non-skipped candidate-SHA real-enclave CI evidence. Never run this allocator-changing
test on a serving/shared host. It proves admission/recovery, not worst-case memory
safety. The listed unit tests cover reinjection; on-call need not time settings changes.

### Release-mode staging smoke

Use the normal deployment/canary procedure, approved non-secret settings,
Kubernetes host/plugin logs and Grafana node/host metrics (Beholder/OTel enabled).
Substitute actual pod/node/collector labels below. The release launcher does not
export guest stderr/kernel logs; do not enable Nitro debug mode to obtain them.

1. Record the candidate SHA/image and approved `maxConcurrentCompilations`
   (default 4). Confirm the host logs "injected storage credentials into enclave"
   without an injection error. Discover fresh memory series for the candidate pod:

   ```promql
   {__name__=~"confidential_compute_enclave_memory_.*", <CANDIDATE_HOST_LABELS>}
   ```

   Divide `memory.total` bytes by 1048576 to obtain rounded guest MiB `T`, not
   the Nitro allocation. Apply the runbook's `ForMemory` formula at `T-1` and
   `T`: these bound execution/compile capacities because startup truncates MiB.
   Cap the approved compilation setting/default by each possible compile capacity.
   Record these expected ranges, not exact limits or observed gate occupancy.

2. Observe a 15-minute normal canary window. Capture status before/after and
   inspect both host and enclave-plugin logs (not guest console logs):

   ```sh
   kubectl --context "$CONTEXT" -n "$NAMESPACE" get pod "$POD" -o json |
     jq '{uid: .metadata.uid, started: .status.startTime,
       containers: [.status.containerStatuses[] | {name, imageID, restartCount, lastState}]}'
   kubectl --context "$CONTEXT" -n "$NAMESPACE" logs "$POD" --all-containers --prefix --since=15m
   kubectl --context "$CONTEXT" -n "$NAMESPACE" get events --field-selector "involvedObject.name=$POD"
   ```

   Confirm canary results and execution IDs in candidate host logs. Check for
   `OOMKilled`, new container/pod restarts, plugin "is no longer running",
   lost enclave connectivity and `ENCLAVE_MEMORY_METRICS_ERR`. Compare fresh
   `memory.available` (sampled window minimum), `memory.rss` (sampled maximum)
   and `memory.rss_peak` (lifetime peak) with the baseline. Gaps or a peak reset
   require investigation; pod restart counts alone cannot exclude a guest OOM.

3. In the node-metrics data source, discover the phase series on one workflow
   DON node; select the canary's discovered workflow/enclave labels as well:

   ```promql
   {__name__=~".*workflow_(compilation_queue_wait|compilation|guest_execution).*", component="enclave", node_id="<NODE_ID>"}
   increase(<PHASE_DURATION_COUNT>{component="enclave", node_id="<NODE_ID>", <CANARY_LABELS>}[15m])
   histogram_quantile(0.90, sum by (le) (rate(<PHASE_DURATION_BUCKET>{component="enclave", node_id="<NODE_ID>", <CANARY_LABELS>}[15m])))
   ```

   Use the discovered histogram names in the last two queries, once per phase.
   Each event produces a counter and duration histogram in seconds. After canary
   success and two exports, all phases must have samples, with `success="true"`
   for compile/guest (no success label for queue wait). Compare latency with the
   agreed baseline. Zero queue wait is valid; missing data/NaN is not zero.
   Do not sum DON nodes or use node-wide traffic as candidate evidence.

4. If normal traffic produces rejections, inspect the node-side event:

   ```promql
   {__name__=~".*execution_rejected_at_capacity.*", component="enclave", node_id="<NODE_ID>"}
   ```

   Correlate rejection logs with the candidate; `max_concurrent` must fit its
   derived range. The counter lacks `enclave.id`, so is not per-pod. Without
   overload, rejection is unexercised: use automated proof, not an absent series.
   Host in-flight gauges include rejected calls, not admission occupancy/percentiles;
   host `executions.rejected` misses app errors wrapped as HTTP 500.

### Deferred calibration

Representative x86_64 cold/warm compilation, execution/download memory and
peak/retained RSS measurements are separate from this smoke, before revising
allowances. ARM remains deferred until platform blockers and hardware are resolved.

## Success criteria

The candidate's automated proof passes; staging canaries succeed with accepted
settings, recorded capacity ranges, all phase metrics and baseline latency/memory.
No unexplained restarts, enclave loss, stuck executions or observed OOMs occur.
Missing telemetry or unresolved failures block sign-off. This does not prove
the absence of every guest OOM or a worst-case memory bound.

## Edge cases and risks

The 128 MiB execution allowance does not fully cover native/runtime or download
overhead; the coefficients are estimates, not hard containment for arbitrary WASM.
Small enclaves have substantially less concurrency; guest RAM below 1664 MiB fails
startup. Monitor large binaries and cold-compilation bursts. Roll back for OOMs,
stuck admission, or unacceptable latency/rejection rates. Changing effective
compilation concurrency requires an enclave restart; unchanged credential
rotations remain supported.
