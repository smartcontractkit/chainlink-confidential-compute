# Staging validation: priv-743-per-capability-limits

## Change

Capability plugin (`capabilities/framework`, both `confidential-http` and
`confidential-workflows`): every Confidential Compute limit now resolves from
the executor's own capability group (`ConfidentialCompute.HTTP` /
`.Workflows`, plus the `PerOwner` rate) first, falling back to the shared
`ConfidentialCompute` value when that key is unset. A limits change aimed at
one capability no longer moves the other. Each executor now logs its fully
resolved config at init (`resolved capability config`). The `chainlink-common`
bump only adds the settings APIs; the enclave image, host and config-tracker are
unchanged.

## Validation steps

1. After the capability plugin rolls to staging, find the init lines in Loki:
   `{cluster="staging-us-west-2-main", namespace="chainlink"} |= "resolved capability config"`
   Expect lines for each executor, tagged with `capabilityID`.
2. Compare the logged values with the node's configured CRE settings. With no
   per-capability override set, the `confidential-http@1.0.0-alpha` and
   `confidential-workflows@1.0.0-alpha` lines must be identical and match the
   shared `ConfidentialCompute` values.
3. Set one per-capability override in the staging CRE settings, for example
   `[global.ConfidentialCompute.HTTP] GlobalRate = 50rps:5000`, and trigger a
   request for both capabilities.
4. Re-read the log: only the `confidential-http` line should change
   (`globalRPS=50`, `globalBurst=5000`), while `confidential-workflows` keeps
   the shared value. Confirm the next `resolved capability config` line shows the
   new value without a pod restart.
5. Unset the override and confirm both lines return to the shared values.
6. Existing canaries: run the standard confidential-http and
   confidential-workflows smoke workflows and check success rate, execution
   latency and rate-limit errors on the Confidential Compute dashboard.

## Success criteria

- Step 1 shows `resolved capability config` lines for each executor, with every
  field populated (rates, retries, timeouts, refresh interval, cache and session
  settings).
- Steps 2 and 5: both capabilities log the same values as each other and as the
  shared settings — rollout is behavior-neutral when no per-capability key is
  set.
- Step 4: only the targeted capability's values change, and the change takes
  effect without restarting the pod.
- Canaries stay green: no new rate-limit, timeout or retry errors, and p99
  execution latency tracks the same baseline as before the roll.

## Edge cases and risks

- Mixed capability-plugin versions during the roll: old plugins ignore the
  per-capability keys and keep reading the shared values, so an override looks
  applied only once every node is upgraded.
- A per-capability value wins over the shared value at every scope until it is
  unset; changing the shared block afterwards does not move that capability.
  This is intended.
- `InsecureSkipTLSVerify` stays shared on purpose (node-wide enclave trust
  posture), so a per-capability override for it does not exist.
- The config line is logged on every execution (limits are re-resolved per run),
  so it adds one info line per request. Query it with a short range, and drop it
  once validation is done if the volume is a concern.
- Roll back if rate-limit or timeout errors increase for either capability.
