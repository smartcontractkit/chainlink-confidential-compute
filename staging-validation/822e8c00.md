# Staging validation: redact-http-errors

## Change

Confidential HTTP and Confidential Workflows replace outbound HTTP errors with
fixed diagnostics before they leave the enclave. Response-close errors are no
longer logged. Both applications require updated trusted enclave images.

## Validation steps

1. Deploy both enclave images through the normal staging release process.
2. Exercise each application against a controlled HTTPS endpoint using a unique,
   non-secret canary in the hostname, path, query, authorization header, and body.
   Disable workflow-authored logging of those values during these checks.
3. Trigger a blocked redirect with the canary in Location, an untrusted or
   mismatched certificate, and failures after response headers (timeout and a
   connection closed before the declared Content-Length is received).
4. Inspect returned errors, enclave and node logs, and Beholder capability events
   for the canary. Confirm the error names the failure category without request
   or response values.
5. Run successful requests and pre-response timeout, DNS, and policy-block cases
   to check that normal responses and existing synthetic HTTP statuses still work.

## Success criteria

- No canary appears in failure diagnostics, logs, or telemetry.
- Redirects are not followed; certificate and response-read failures remain hard
  failures. Read timeouts and truncated bodies retain their fixed diagnostics.
- Successful requests and existing synthetic response statuses are unchanged.

## Edge cases and risks

Unknown failures intentionally lose their raw details. Hostnames and certificate
names must remain redacted too. Partial response bodies must not accompany read
errors. Workflow-authored logs and successful response payloads are outside this
redaction boundary. Any canary disclosure or change in failure classification
blocks release; this plan is not evidence that staging has already been run.
