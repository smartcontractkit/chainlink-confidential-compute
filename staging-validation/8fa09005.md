# Staging validation: priv-707-relay-callback-id

## Change

The confidential-workflows enclave sends the relay DON a callback ID for
runtime `GetSecrets` derived from the request (enclave key, config, secrets),
so a retry on an enclave with a different key gets a fresh result instead of
the one signed for the previous key. Ships in the confidential-workflows
enclave only; no node or relay change.

## Validation steps

- Run a confidential workflow that calls `GetSecret` and confirm it succeeds.
- In the enclave logs, find `[remoteDispatcher] derived relay callback ID for
  secrets request` for that execution and note `callbackID` and the negative
  `relayCallbackID`.
- In the relay node logs for the same execution, confirm `fetched and signed
  secrets response` carries key `get-secrets/<workflowID>/<executionID>/<relayCallbackID>`.
- Force a key change mid-execution: while the workflow is fetching secrets,
  delete one `enclave-workflows-*` pod with `--grace-period=0 --force`, so the
  executor retries the execution on the other replica.
- Watch the existing confidential workflows canaries and the GetSecrets
  success-rate panel on the Confidential Compute dashboard for the soak period.

## Success criteria

- Every runtime `GetSecrets` logs a negative `relayCallbackID`, and the relay
  memo key uses it.
- The execution retried after the forced pod deletion completes; no
  `no relay-DON result reached quorum` error with `0 valid signatures` appears
  on the GetSecrets path.
- Canaries stay green and the GetSecrets success rate and latency are unchanged.

## Edge cases and risks

- Relay and vault logs and the CRE UI get-secrets step show the derived negative
  ID instead of the WASM call number; the enclave mapping log bridges them.
- A re-fetch after a key change is charged again against `Secrets.CallLimit`
  (default 5 per execution); workflows near the limit can fail on retry.
- Enclaves on the previous version keep the old behavior until replaced.
- Roll back by redeploying the previous enclave image; there is no node-side
  state to undo.
